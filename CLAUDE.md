# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Research code for a thesis on **ML utility loss**: a differentiable neural network that *estimates* the machine-learning utility of synthetic tabular data, so that estimate can be used as a training loss (and its gradient) to guide tabular data synthesizers toward higher-utility output.

Two halves of the idea live under `ml_utility_loss/loss_learning/`:

- **`ml_utility/`** — the *ground-truth* utility. `eval_ml_utility()` (in `ml_utility/pipeline.py`) trains CatBoost on `(train, val, test)`, selects on `val`, and scores `test` with F1 / R2 / etc. Two-way calls train without an evaluation set. This is the real, non-differentiable number the estimator learns to imitate. Falls back to `NaiveModel` when CatBoost can't fit (constant target, etc.).
- **`estimator/`** — the *learned, differentiable* utility. A set-transformer-style model (`MLUtilityWhole`) is trained to predict CatBoost utility from raw (train, test) sets and applies a heuristic gradient penalty intended to make the estimate usable as a synthesizer loss; it is not supervised with true-utility gradients.

## Current Research Status

Prior experiments do **not** establish that MLU improves strong synthesizers. Their utility labels and estimator selection reused holdouts; their downstream objective targeted sampled historical values; and the gradient penalty had no measured true-utility direction. Regenerate all cached labels and rerun comparisons after the following code changes.

- `eval_ml_utility()` now accepts `(train, val, test)`, derives multiclass labels from train/validation data only, uses only `val` for CatBoost early stopping, and scores only `test`. A two-way call trains CatBoost without an evaluation set. `augment_kfold()` now requires three partitions, generated folds vary by augmentation level, and all synthesizer studies propagate the three partitions when provided.
- Estimator training now requires three datasets to use validation; with two datasets it does not inspect the test set during epochs, scheduling, or early stopping. The heuristic gradient penalty is disabled by default (`GradientPenaltyMode.NONE`).
- `MLUtilityTrainer(target=None)` now directly maximizes the surrogate estimate instead of matching a sampled historical label. It skips disconnected optimizer parameters; LCT autoencoder sampling now generates exactly `n_samples`; and LCT-GAN MLU sampling keeps BatchNorm in inference mode.
- Direct surrogate maximization still does not establish a correct utility gradient. The guided tensor remains mismatched for TVAE/LCT-GAN soft outputs, REaLTabFormer hidden states, and hard categorical/token sampling. Do not enable the heuristic gradient penalty or make quality claims without the gates below.

Do not tune MLU hyperparameters or make quality claims until these gates pass:

1. Split real data into generator training, CatBoost tuning/early-stop, and untouched final utility test partitions.
2. Evaluate paired baseline-vs-MLU runs across repeated seeds and report the held-out utility delta with uncertainty.
3. Hold out complete generator runs/source folds for surrogate calibration and rank-correlation tests.
4. Test local guidance directly: an MLU-proposed generator update must beat an equal-norm random update on true held-out utility.
5. Begin with a continuous, representation-aligned synthesizer; preserve its native objective and add only a small, annealed MLU auxiliary loss.

`loss_learning/evaluation/experiments.py` provides optional three-way splits, paired benchmark runs, and equal-norm local-update comparisons; callers supply synthesizer-specific callbacks.

### Diagnosis: why prior MLU runs failed (2026-07-11)

Observed symptom: MLU improved only weak synthesizers, inconsistently, and never improved strong ones. This is the signature of a **weak, biased proxy gradient**: a bad synthesizer has enough true-utility headroom that even a loosely-correct push helps, while a strong one sits near the utility ceiling where surrogate bias/noise exceeds the remaining true signal (Goodhart). Root causes, grounded in the code:

1. **Label + selection leakage.** Old `eval_ml_utility()` scored utility on the same holdout later reused for estimator selection/eval, so surrogate labels were optimistic and miscalibrated. Fixed to a 3-way split, but all cached labels and every prior comparison are leaked and must be regenerated.
2. **The surrogate gradient is never supervised toward true utility — and cannot be.** CatBoost is non-differentiable, so a ground-truth `∂utility/∂samples` does not exist to train against. The estimator only fits the utility *value* (`F.mse_loss(est, catboost_value)`); its input→output gradient is an unconstrained byproduct. The heuristic gradient penalty (`calc_g_loss` → `calc_g_mse_mag_loss`/`calc_g_mag_corr_loss`/cos terms in `estimator/process.py`) shapes only gradient *magnitude* (`get_g = target*|error|`) and sign-correlation — no term constrains *direction* toward higher true utility. Correctly disabled now (`GradientPenaltyMode.NONE`); the differentiable-gradient premise remains unvalidated.
3. **Old downstream objective pushed toward an arbitrary label.** `MLUtilityTrainer(target=X)` minimized `MSE(est, X)` against a sampled historical value; when `X < est` it pushed utility *down*. Fixed to `target=None → loss=-mean(est)` (`estimator/wrapper.py`), but maximizing an unvalidated surrogate just searches its blind spots.
4. **Gradient applied to the wrong tensor (guided-tensor mismatch).** The synthesizers do not share one bug — each `sample(raw=True)` path was audited separately (see the per-synthesizer table below). TVAE had a genuine wrong-activation bug (blanket `torch.tanh` over softmax categorical spans); LCT-GAN is actually correct; tab_ddpm and REaLTabFormer have a deeper dead-gradient problem through discrete sampling.
5. **Off-distribution estimator input.** The estimator is trained on preprocessed real/augmented tables but fed raw decoder tensors at guidance time, so predictions are least reliable exactly where they are used.
6. **Utility defined by one CatBoost config/metric.** The surrogate mimics one model's idiosyncrasies; a strong synthesizer already captures that signal, so extra MLU pressure chases CatBoost-specific quirks rather than model-agnostic utility.
7. **Sampling artifacts** (LCT-GAN BatchNorm in train mode during sampling, wrong LCT-AE sample count) injected variance; both already fixed.
8. **Ground-truth labels never used a real CatBoost fit.** Verified 2026-08-08 (see "CatBoost noise floor measurement" below): every cached `real_value`/`synth_value` in `aug_train/<dataset>/all/info.csv` matches `eval_ml_utility()` called with `CatBoostModel`'s bare defaults — `epochs=1`, `lr=0.1`, no depth/subsample/regularization tuning, `random_seed=42` — to full float precision, across all four datasets. The tuned `BEST` hyperparameters in `ml_utility/params/<dataset>.py` were never applied to label generation; on insurance this is the difference between R2 0.134 (cached) and R2 0.845 (BEST, same data). A single-iteration CatBoost fit is close to one decision stump: the "ground truth ML utility" every estimator number in this file is regressed against is a noisy, near-degenerate score, not the properly-tuned utility `eval_ml_utility()`'s docstring and this file's own "What this project is" section describe. This does not itself explain the weak-synthesizer-only pattern (item 1, Goodhart, still applies), but it means gate 3 (rank-correlation) and every `pred_rmse`/`pred_spearman` figure to date were fit against this degenerate target, not real utility — regenerating labels (fix item C) must also fix `epochs=1`, not just the 3-way split.

Fix priority:

- **Gate A first (go/no-go):** run `evaluation/gate_a_tvae.py:run_gate_a` (built on `experiments.py:run_local_update_test`) — one MLU decoder step must beat an equal-norm *random* step on true held-out utility across seeds. Pass a trained `TVAEModel`, its `DataTransformer`, and a trained `MLUtilityWhole`; Gate A passes only if the summary's `ci95_low > 0`. It fails fast if the generator and estimator `DataTransformer`s have mismatched `output_dimensions`. - **C.** Regenerate all labels 3-way **and with a real CatBoost fit** — the current cache used `epochs=1` (item 8), not just an unleaked split.
- **D.** If Gate A fails, treat MLU as a black-box score (best-of-n / rerank / ES), sidestepping the direction problem.
- **E.** Start with a continuous, representation-aligned synthesizer (native loss preserved, small annealed MLU auxiliary); avoid hard categorical sampling initially.

### Efficiency and tuning audit (2026-07-30)

Separate from the correctness gates above: the estimator's training loop, data path, and Optuna search all waste large multiples of their necessary cost. Measured against the current code and the cached `aug_train/*/all/info.csv` labels. Ordered by payoff per unit of effort.

**Read the findings below as the state on 2026-07-30, not as the state now.** They are kept in the present tense as the original diagnosis; most have since been acted on. The dated "Applied" lists that follow, and the "Still open" list at the end of the section, are what is actually true of the code today.

**Correctness flag first.** `train()` evaluates on `test_set` at the end of `estimator/pipeline.py`, and `study.py:objective` selects hyperparameters on that value, because `eval_val=False` is the default. Estimator hyperparameter selection therefore reads the final test partition — the same leakage class already flagged for labels. Set `eval_val=True` whenever three datasets are supplied and reserve `test_set` for the final report.

Throughput, `estimator/process.py`:

- `clear_memory()` (`util.py`: `torch.cuda.empty_cache()` + `gc.collect()`) runs three times per batch inside `train_epoch` and again inside the evaluation loop. `empty_cache` returns blocks to the driver so the next allocation hits `cudaMalloc`, and `gc.collect()` walks the whole pandas/torch/optuna object graph. One call per epoch is enough; keep the OOM-recovery call in `study.py`.
- About twenty forced device syncs per batch: nine `try_tensor_item` calls in the accumulator block, plus `assert torch.isfinite(...).all()` in `forward_pass_1`, `forward_pass_2`, `forward_pass_gradient`, and the pre-backward block. Accumulate loss statistics as tensors and take one `.item()` per epoch; put the finite asserts behind a debug flag (they exist to feed the "has nan" prune in `study.py`).
- The evaluation loop hardcodes `mag_loss=True, mag_corr=True, cos_loss=True` and calls `calc_gradient(..., create_graph=True)` regardless of `GradientPenaltyMode.NONE`, so every evaluation builds a second-order graph for metrics that have no true-utility supervision. Gate it behind a flag and evaluate under `no_grad`.
- No AMP, no TF32, no `torch.compile`, no `F.scaled_dot_product_attention` anywhere in the package. `torch.set_float32_matmul_precision("high")` is a one-line start. SDPA can only replace the hand-rolled `matmul`+softmax in `estimator/model/modules.py:ScaledDotProductAttention` when `softmax is nn.Softmax` and `attn_residual` is off — the custom-softmax path is load-bearing. `torch.compile` is not worth it: `SizeScheduler` changes shapes and forces recompiles. **Corrected 2026-07-31: that reason is invalid** — `torch.compile(dynamic=True)` and `torch._dynamo.mark_dynamic(tensor, dim)` exist for exactly this, and `SizeScheduler` varies only two dimensions. Whether compile pays under short pruned trials is still open; the stated blocker was not one.

Data path, `estimator/data.py` and `estimator/pipeline.py:load_dataset`:

- `load_dataset` selects `CacheType.PICKLE`, so every sample is a `torch.load` from disk on every epoch, serial (`dataloader_worker=0` default), with no `pin_memory` and blocking `.to(device)`. The preprocessed tensors for one dataset are on the order of a hundred megabytes, so `CacheType.MEMORY` fits and removes the per-epoch disk round trip.
- The cache is keyed by row index, but the underlying files are not unique per row. `aug_train/contraceptive/all/info.csv` has 400 rows and only **five** distinct `test` files, five distinct `val`, and five distinct `train`; only `synth` is 400-unique. The right branch of the model is therefore re-read, re-preprocessed (TVAE BGM transform / `lct_ae.encode`), and re-encoded about eighty times per epoch for no new information. Key the tensor cache by file path. Caching the encoder output `m_test` per unique file is valid too — with PMA on (`tf_pma_start=-1`) the encoder is permutation-invariant, so the per-read row shuffle does not change it — but dropout makes it stochastic in train mode, so cache in evaluation only or accept fixed test embeddings.

Optuna search, `estimator/study.py` and `estimator/params2/`:

- **No pruning exists.** `trial` reaches `train_2`/`train_3` and is used only to build `run_name`; there is no `trial.report` or `should_prune` anywhere in the estimator path. Every trial runs its full `epochs` (search range 100–1000). Reporting the per-epoch `val_value` and adding a `HyperbandPruner` is the single largest tuning win available.
- `SizeScheduler` already ramps dataset size 32 to 2048 while shrinking batch size. That is Hyperband's rung structure built by hand — report at each size step and let ASHA kill trials at low fidelity, where they are cheap.
- Roughly twelve of about forty-five search dimensions are dead. `params2/default.py` pins `gradient_penalty_mode` to `["ONCE"]` while the code default is `GradientPenaltyMode.NONE`, so `g_loss_mul`, `mse_mag*`, `mag_corr*`, `cos_loss*`, and `grad_loss_fn` tune a term that must stay off. Separately, `train(single_model=True)` is the default, which reduces `models` to the role model alone, so `non_role_model_count == 0` and `adapter_loss_fn` / `non_role_model_mul` / the embed-loss path never fire.
- `objective_2` is multi-objective, which disables pruners and weakens TPE; under `single_model=True` its second term is degenerate. Use single-objective unless several adapters are actually being trained.
- One seed per trial (`objective(seed=0)`, `objective_2(seed=42)`) means trial noise gets selected on. Search with one seed, then re-run the top configurations over three to five seeds and pick on the mean.
- `objective` returns raw `pred_rmse`, which is not interpretable and not comparable across datasets. Cached label variance is 0.0113 (contraceptive), 0.0018 (insurance), 0.0644 (treatment), 0.0975 (iris) — a constant predictor already reaches RMSE 0.043 on insurance. Report normalized RMSE or R², and add Spearman, since gate 3 is a rank-correlation gate.

Model and learning:

- **Targets are unstandardized and nearly constant, and that is the root of the std-penalty scaffolding.** Insurance `real_value` spans 0.130–0.144 and `synth_value` reaches −0.018, while the head ends in sigmoid or `leakyhardsigmoid` and cannot represent a negative label at all. MSE is then dominated by an offset the model learns as a constant, prediction variance collapses, and the code fights that symptom with `calc_std_loss`, `mean_penalty_log_half`, `allow_same_prediction`, and the "predicts the same for every input" prune. Standardize `y` per source dataset — `BaseDataset.calculate_stats_` already computes mean/std/range/iqr and they go unused for this — then use a linear head and delete the std penalty. Net deletion of code.
- Pure per-sample MSE optimizes calibration, not ranking, but gate 3 is graded on rank correlation. Add a pairwise ranking term over pairs within a source dataset alongside the MSE.
- The estimator trains on preprocessed real/augmented tables and is fed raw decoder tensors at guidance time (diagnosis point 5). The cheapest countermeasure is to mix decoder-produced tensors from a trained TVAE into the training set, labelled by `eval_ml_utility` on the decoded table. Gated on Gate A being worth running at all.
- `create_model` silently forces `dropout=0` when `layer_norm=True`. Today `layer_norm` is fixed False in `DEFAULTS` so nothing breaks, but a trial that flips it silently discards the tuned `dropout` dimension. Make it an explicit prune or a conditional in the search space.

Suggested order at the time — all of it has since been done, in this order: strip the per-batch `clear_memory()`, switch the cache to memory, delete the dead search dimensions, and set `eval_val=True` (all small edits); then add pruning; then standardize the target.

### What the literature review concluded (2026-07-31)

Five passes are recorded below. This is what they add up to. **Read this before the passes; the passes are the evidence.**

The structural finding: **the value prediction is sound, the gradient is the unsupported leap.** Predicting a scalar quality score from a dataset is a solved problem type — algorithm selection, NAS predictors, neural processes and learning-loss modules all do it. ### Quick wins implementation (2026-08-08)

All five items from the "Quick wins" list above, plus one bug found while verifying them. Verification: unit tests for the pure-function pieces (`pairwise_rank_loss`, the `tf_num_inds` sampler, the SDPA-vs-hand-rolled numerical equivalence, the `RandomSampler` epoch-fraction mechanism), plus real-pipeline smoke tests against `params2.contraceptive.BEST_DICT["tab_ddpm_concat"]` and cached `aug_train/contraceptive/` data (same pattern as the training-loop profile above).

- **`rank_loss_mul` — LearningLoss++, on by default.** `metrics.pairwise_rank_loss` rewritten from vanilla RankNet to the LearningLoss++ form (Shukla & Ahmed, CVPR-W 2021): each ordered pair's target is `sigmoid(y_i-y_j)` instead of a hard 1/0 sign label, so a barely-separated pair contributes a small loss regardless of how confidently the network mispredicts its order, and a wide gap recovers the exact old RankNet term as a limit (proved and checked numerically: `y_gap=20` reproduces `softplus(-(pred_i-pred_j))` to 1e-5). `rank_loss_mul` default flipped `0.0` → `0.5` in both `pipeline.train()` and `process.train_epoch()`.
- **`tf_num_inds=0` excluded.** `params/default.py` and `params2/default.py` had `"bool_int_exp_2"` (samples `False`/0 in addition to the stated range); every per-dataset override already used plain `"int_exp_2"`, so this closes the one hole. Verified: 200 simulated Optuna trials against the new space never sample 0.
- **`torch.set_float32_matmul_precision("high")`** set globally in `util.py` next to `DEFAULT_DEVICE`.
- **Conditional SDPA, on by default.** `ScaledDotProductAttention.forward` now calls `F.scaled_dot_product_attention` whenever `type(self.softmax) is nn.Softmax` (the only case it can express — `sparsemax`/`entmax15`/`relu15` fall back to the hand-rolled path unchanged) and skips returning per-head attention weights, which nothing in the package reads (`return_attns=True` appears nowhere — checked by grep). Verified numerically equivalent to the old matmul+softmax path to ~5e-7 max abs difference, with and without `attn_residual`, and that the custom-softmax fallback still returns real weights.
- **`amp_dtype`, opt-in bf16 autocast.** Threaded through `pipeline.train()` → `process.train_epoch()`/`process.eval()` as `amp_dtype=None` (default, unchanged behavior). When set, wraps the per-batch forward+loss region (and, for a much smaller diff than reindenting ~250 lines, backward too — harmless for bf16, which replays the dtype recorded on the autograd graph during forward regardless of the ambient autocast state at backward time; costs a negligible dispatch check). **Real-pipeline result: correct but not fast here.** `amp_dtype=torch.bfloat16` produced finite train and eval losses through the real `tab_ddpm_concat` model including the new SDPA path, but took **~30x longer** than fp32 for identical batches (270s vs 9s for 2 batches) — this CPU (AMD Zen2, no AVX512-BF16) has no hardware bf16 path, so autocast falls back to software emulation. Left opt-in rather than defaulted on; the intended payoff is CUDA tensor cores, unverified on this hardware.
- **`epoch_frac`, opt-in spaced-repetition subsampling.** `pipeline.train()`'s `prepare_loader` closure now takes `epoch_frac=None` (default, unchanged behavior); when set, the training loader uses `RandomSampler(dataset, replacement=False, num_samples=int(len(dataset)*epoch_frac))` instead of `shuffle=True`. `RandomSampler.__iter__` draws a fresh truncated permutation every time `DataLoader` re-iterates it, i.e. every epoch, with no other change needed to the epoch loop — verified in isolation (100-item dataset, `epoch_frac=0.4`: 40 items/epoch, no duplicates, three different subsets across three epochs) and against the real pipeline (`epoch_frac=0.1` on the real 805-example `contraceptive` pool: exactly 80 train examples, 10 batches at `batch_size=8`, val unaffected at its full 200/25). Orthogonal to `SizeScheduler`, which controls rows sampled per table, not which labeled examples train this epoch.
- **Bug found while verifying, not fixed (out of scope): `Timer(max_seconds=...)` never reaches `train_epoch()`/`eval()`.** See the "still open" diagnosis list above — `train()` never passes its `timer` into the inner calls, so `max_seconds` is only checked between epochs, not per-batch as the code inside `train_epoch` implies. A full epoch over the real ~800-example pool can run many minutes past the requested budget.

### Literature review (2026-07-31)

A survey of published work against this architecture (set transformer over two row-sets, per-synthesizer adapters, MSE on ~400 labels per dataset, graded on Spearman). Every claim below was checked against the source rather than a search summary, and the entries record the criticism as well as the result. Nothing here has been implemented.

**Act on these.**

- **The objective is the problem, not just the target scale.** [Learning Loss for Active Learning](https://openaccess.thecvf.com/content_CVPR_2019/html/Yoo_Learning_Loss_for_Active_Learning_CVPR_2019_paper.html) (Yoo & Kweon, CVPR 2019) is the same design as MLU — a bolted-on module predicting a scalar the real computation is too expensive to give. They **tried MSE and it failed**, because the true target's scale drifts, and switched to a pairwise ranking loss that discards scale. The `calc_std_loss` / `mean_penalty_log_half` / `allow_same_prediction` / "predicts the same for every input" scaffolding here is that same collapse. Standardizing `y` treated the symptom. Use [LearningLoss++](https://openaccess.thecvf.com/content/CVPR2021W/TCV/papers/Shukla_A_Mathematical_Analysis_of_Learning_Loss_for_Active_Learning_in_Regression_CVPRW_2021_paper.pdf) (CVPR-W 2021), which shows the original ranking loss *wrongly penalizes* the network in specific cases, rather than vanilla RankNet — ~~`metrics.pairwise_rank_loss` is currently the vanilla form~~ **implemented 2026-08-08, see "Quick wins implementation"**. [Listwise](https://arxiv.org/pdf/2008.00078) (arXiv 2008.00078) optimizes Spearman directly, which is what gate 3 grades — not implemented; `pred_spearman` is currently a monitoring metric, not a training target.
- **`SizeScheduler` is the part of curriculum learning that survived replication.** [When Do Curricula Work?](https://arxiv.org/abs/2012.03107) (Wu, Dyer, Neyshabur, ICLR 2021 oral) found curriculum helps only under a limited training budget or noisy labels, and that "any benefit is entirely due to the dynamic training set size" — which is what `SizeScheduler` does and difficulty-ordering does not. Both qualifying conditions hold here (CatBoost early-stopping variance makes the labels noisy; the budget is limited), so ordering is not ruled out, it is just not free.
- **[Spaced repetition](https://aclanthology.org/D17-1255/)** (Amiri et al., EMNLP 2017): 34–50% of the data per epoch, 2.9–4.8× faster training. Scheduler-level, composes with `SizeScheduler`. **Implemented 2026-08-08** as `epoch_frac` — see "Quick wins implementation"; not defaulted on, the 2.9-4.8x figure is unverified here.
- **Cheapest possible falsification first.** [How Powerful are Performance Predictors in NAS?](https://arxiv.org/abs/2104.01177) (White et al., NeurIPS 2021) compares 31 predictors under budget constraints and finds the best choice is budget-dependent and that predictor *families combine* to beat any single one. Run a random forest on engineered meta-features as a baseline before spending more GPU on the set transformer — if it matches `pred_spearman`, the architecture work is unjustified.
- **Stop searching `tf_num_inds=0`.** `params2/default.py:151` allows it, which drops `EncoderLayer` to full `SimpleMultiHeadAttention` over 2048 rows — a 2048×2048 map, ~537MB per attention at batch 4 × 8 heads in fp32. With `tf_num_inds=64–128` (the `BEST` values) attention is already 128×2048 and linear in set size. **Implemented 2026-08-08** — see "Quick wins implementation".

**Promising, with the caveat stated.**

- **TabPFN for label cost, not (yet) for gradients.** [TabPFN](https://arxiv.org/abs/2207.01848) predicts in one forward pass with no fitting — 230× faster than AutoML, 5700× on GPU — which would make the 3-way relabel (item C) and the model-ensemble utility (item G) affordable. [A Closer Look at TabPFN v2](https://arxiv.org/html/2502.17361v1) (261 datasets) gives the v2 envelope: **≤10,000 samples, ≤500 dimensions, ≤10 classes**; outside it TabPFN v2 ranks 3.97 vs CatBoost 1.89 on large data and *loses to logistic regression* (3.36 vs 2.27) above 2000 dimensions. Every dataset here is inside the envelope. **Superseded — see the third pass below: TabPFN-2.5 raises this to 50,000 rows and 2,000 features.** Separately: **no paper establishes `∂prediction/∂(in-context rows)`** — the differentiability in the codebase is for fine-tuning parameters. Treat "TabPFN supplies the missing utility gradient" as an untested hypothesis, gated behind Gate A.
- **[Dataset Policy Gradient](https://arxiv.org/html/2604.08423)** is the formal version of what MLU approximates: optimize a generator for a differentiable downstream metric using metagradients through the target model's training, with an error bound. It confirms the blocker rather than solving it — the framework requires backprop through target-model training and **does not handle gradient boosting**. Also only works with Adam in the metagradient, which the authors flag as a theory gap. Read before redesigning the guidance loop.
- **[EvoMAL](https://www.computer.org/csdl/journal/tp/2023/11/10177983/1OH1ukwC7iU)** (Raymond et al., TPAMI 2023) and [Meta-Learning Adaptive Loss Functions](https://arxiv.org/abs/2301.13247) are the loss-function-learning literature this thesis belongs in. Their tri-level framing (loss structure, then loss weights, then model) is the vocabulary for what MLU does informally. Positioning, not engineering.

**Tempered or demoted after checking the criticism.**

- **SDPA + bf16 are coupled and worth less here than the headline numbers.** PyTorch's "20–110% memory, 10–70% speedup" was measured on decoder LLMs with square causal attention; this code's attention is 128×2048, already linear, so the main Flash win does not apply. FlashAttention-2 also [does not support fp32](https://github.com/Dao-AILab/flash-attention/issues/915) — in fp32 PyTorch silently falls back to the memory-efficient or math backend. Realistic gain ~10–25%, and bf16 with **no normalization anywhere** (`layer_norm` pinned False) needs a numerics check, not a blind switch. **Implemented and numerics-checked 2026-08-08** — see "Quick wins implementation": SDPA on by default, bf16 opt-in. The numerics check passed (no NaN/Inf on real batches); the speed claim did not transfer to this CPU dev box, which measured bf16 **~30x slower**, not faster — a hardware gap (no AVX512-BF16), not a correctness one, but a reminder that none of the SDPA/bf16 numbers above have been checked on this project's actual CUDA target either.
- **muP** ([Tensor Programs V](https://arxiv.org/abs/2203.03466)) — demoted. [u-µP](https://arxiv.org/html/2407.17465v1) reports the standard application "does not give effective transfer for Llama-style models"; [Weight Decay may matter more than muP](https://arxiv.org/pdf/2510.19093) argues independent weight decay, not µP, does the stabilizing; an [independent reproduction](https://openreview.net/forum?id=AFxEdJwQcp) notes it "has not gained much traction". Transfer also breaks on trainable norm gains, per-layer bias, and optimizer choice — all of which this code varies. The cheap version (tune at `d_model=64`, spot-check the top-k at 256) needs no reparametrization.
- **DyT** ([Transformers without Normalization](https://arxiv.org/html/2503.10622v1), CVPR 2025) — demoted. All favourable results are author-reported, and follow-up work says norm-free methods "remain fragile at depth" and DyT "does not explicitly control how output mean and variance grow with depth". Poor fit for a network that already has no normalization.
- **Schema-invariant encoding** ([Dataset2Vec](https://arxiv.org/abs/1905.11063), [SAINT](https://table-representation-learning.github.io/assets/papers/saint_improved_neural_networks.pdf), [XTab](https://arxiv.org/pdf/2305.06090)) would remove the per-synthesizer `DEFAULT_ADAPTER_DIMS` and let one model see all four datasets' labels at once. But Dataset2Vec's advantage was measured across 120 datasets and this project has **4**, where learned meta-features are as likely to memorize the source table. Revisit if the dataset count grows. Note also [Grinsztajn et al. NeurIPS 2022](https://arxiv.org/abs/2207.08815): tree models still beat tabular DL after equal tuning, and that benchmark exists precisely because SAINT-era papers tuned unequally.
- **General caveat on the NAS-predictor transfer.** NAS-Bench-101 has 423k labelled architectures in one homogeneous space. This project has ~1600 labels over 4 datasets and 5 distinct source tables. The direction of those findings transfers; the effect sizes do not. Below the scale at which any of these methods were validated is an argument for cheap baselines and more labels, not more architecture.

**Ruled out.**

- **Nyströmformer** — its landmark attention is the same trick as ISAB's inducing points, already implemented at `modules.py:511` with learned rather than pooled landmarks. Lateral move. The 2021 linear-attention race was largely settled by making *exact* attention IO-efficient.
- **GFNet / FFT token mixing** — learnable global filters are position-dependent over a fixed grid. The input here is an unordered set; there is no frequency axis, and using one destroys the permutation invariance the PMA/ISAB design exists to guarantee.
- **Low-rank factorization references (EdgeFace LoRaLin and similar)** — already implemented as `LowRankLinear` / `LoRALinear` in `modules.py:102-159`.
- **Deep-generative oversampling for imbalanced classes** — touches `augment_2()`/`augment_kfold()`, not the estimator. Keep [Camino et al.](https://arxiv.org/abs/2005.03773) as prior art for the pattern this project keeps hitting: significant when ranked, "often minor in absolute terms".

### Literature review, second pass (2026-07-31)

Snowballed from the seeds above. Five threads the first pass missed. The first one is the measured theory of the failure recorded under "Diagnosis".

**Reward-model overoptimization is this project's failure mode, and it has been measured.** MLU maps onto RLHF exactly: a learned scalar proxy trained on labels from an expensive oracle, then optimized against by a policy. [Scaling Laws for Reward Model Overoptimization](https://arxiv.org/abs/2210.10760) (Gao, Schulman, Hilton, ICML 2023) shows the gold score rises, peaks, then falls as the proxy is optimized, and fits it with d = √KL from the initial policy: best-of-n follows `R(d) = d(α_bon − β_bon·d)`, RL follows `R(d) = d(α_RL − β_RL·log d)`, coefficients scale smoothly with proxy size, and **more proxy training data raises the peak**. For BoN the budget is analytic: `KL = log n − (n−1)/n`.

That is the shape of "MLU helped weak synthesizers and not strong ones" — a weak generator sits far from the peak with headroom, a strong one is already past it. The Diagnosis section calls this Goodhart informally; this is the citation, and it supplies a measurable x-axis. Caveat: their setup is synthetic (the "gold" is itself a model) and entirely LLM-domain, so import the shape and the cause, not the fitted constants.

Two consequences:

- **Best-of-n should be promoted from fallback to primary.** Fix item D currently treats it as what to do if Gate A fails. BoN has a measured overoptimization curve *and* an analytic KL budget; gradient guidance has neither, and its direction is still unvalidated. **Mechanism implemented 2026-08-08** as `estimator/selection.py:best_of_n` — see "Big wins implementation"; wiring it into a specific synthesizer's sampling loop is not done.
- **Ensemble plus conservative scoring is the concrete form of fix items F and G.** [Reward Model Ensembles Help Mitigate Overoptimization](https://arxiv.org/abs/2310.02743) (Coste et al., ICLR 2024) finds worst-case and uncertainty-weighted objectives *practically eliminate* overoptimization for BoN (up to 70% better) and, for PPO, prevent it at no performance cost when combined with a small KL penalty — tested with 25% label noise. Cost is honest: k estimators means k× training, and the conservative objective needs a meaningful uncertainty estimate. [Lil'Log on reward hacking](https://lilianweng.github.io/posts/2024-11-28-reward-hacking/) is the survey entry point and is candid that mitigation work is thin. **Mechanism implemented 2026-08-08** as `estimator/selection.py:conservative_score` — see "Big wins implementation"; the k-estimator training cost is real and unpaid (needs k real `train()` runs).

**Dataset distillation is the adjacent field this project does not cite.** "Optimize synthetic data so a model trained on it performs well" is that field's definition ([survey](https://arxiv.org/html/2301.05603v4)). Most of it needs a differentiable downstream model — the same blocker as DPG — with one exception: **distribution matching** (MMD between real and synthetic features) never differentiates through training and is therefore compatible with a non-differentiable CatBoost oracle. Weaker signal than the objective actually wanted, but a real gradient instead of an unvalidated one. The field's known failure mode is also a warning: distilled sets are architecture-specific and transfer poorly across downstream models, which is Diagnosis item 6 arriving independently from another literature.

**Three literatures converge on pairwise, and the reviews say how to build it.** [BRP-NAS](https://arxiv.org/abs/2007.08668) (NeurIPS 2020) converts accuracy prediction into a binary relation — which of two candidates is better, never an absolute value — plus iterative data selection focused on top candidates. The [NeurIPS reviews](https://proceedings.neurips.cc/paper_files/paper/2020/file/768e78024aa8fdb9b8fe87be86f64745-Review.html) found their predictor **is not symmetric** (a joint classifier over concatenated embeddings does not guarantee `F(m1,m2)` agrees with `F(m2,m1)`) and that **cycles** are unhandled. Both defects vanish if the pairwise decision is a difference of scalar scores — which is what `metrics.pairwise_rank_loss` already is. So: keep the score-difference form, adopt the iterative top-focused selection, reject the joint-classifier head. Active learning, NAS, and learning-to-rank reached the same conclusion about absolute regression independently.

**A theoretical limit that may or may not bind — do not cite it as settled.** [On the Limitations of Representing Functions on Sets](https://proceedings.mlr.press/v97/wagstaff19a.html) (Wagstaff et al., ICML 2019, extended [JMLR 2022](https://arxiv.org/pdf/2107.01959)) proves that continuous *sum-decomposable* Deep Sets need latent dimension ≥ M to represent functions on sets of size ≤ M. With `dataset_size=2048`, `d_model` 64–1024 and `head_n_seeds=1` that sounds fatal — but the extended paper does not visibly address attention pooling, and PMA's weights depend on the whole set, so it is not obviously in scope and no proof either way was found. Settle it empirically instead: sweep `d_model` and `head_n_seeds` against `dataset_size` and check whether error grows with set size at fixed latent width. Cheaper than reading further.

**Label triage, with the replication caveat and a control.** [Deep Learning on a Data Diet](https://arxiv.org/abs/2107.07075) (Paul et al., NeurIPS 2021) scores examples by GraNd/EL2N; [a replication](https://openreview.net/forum?id=1dwXa9vmOI) confirms EL2N but finds **GraNd-at-initialization does not reproduce** — which was the cheap variant. Use EL2N, which needs a few epochs. The relevance here is inverted from the paper's: the bottleneck is not surplus labelled data, it is that each label costs a CatBoost fit, so the scores rank *which augmented tables to label next*. Pair that with [Munjal et al., CVPR 2022](https://openaccess.thecvf.com/content/CVPR2022/html/Munjal_Towards_Robust_and_Reproducible_Active_Learning_Using_Neural_Networks_CVPR_2022_paper.html): active-learning gains over **random sampling** are inconsistent and vanish under strong regularization. That does not touch the Yoo & Kweon finding above (mechanism, not benchmark), but any selection scheme needs a random-selection control — the same discipline Gate A already applies.

**[Task2Vec](https://paperswithcode.com/paper/task2vec-task-embedding-for-meta-learning)** (Achille et al., ICCV 2019) embeds a dataset via the Fisher information of a probe network. It answers the objection raised against Dataset2Vec above: it is *computed*, not meta-trained across many datasets, so it works at four datasets where learned meta-features would memorize the source table. It is dataset-level only and cannot express per-row structure, so use it as features for the random-forest baseline, not as a replacement encoder.

**Unverified, but it targets the ground truth.** [Systematic Assessment of Tabular Data Synthesis](https://arxiv.org/pdf/2402.06806) has a section titled "Limitations of Machine Learning Efficacy". The PDF did not parse, so this is a pointer rather than a summary — read it directly, because ML efficacy *is* `eval_ml_utility()`, and a documented limitation there propagates to every cached label and every gate.

### Literature review, third pass — latest first (2026-07-31)

**The tabular foundation model envelope recorded above is out of date.** [TabPFN-2.5](https://arxiv.org/html/2511.08667v2) handles **50,000 rows and 2,000 features** — twenty-fold in each dimension over v2 — with a reported 100% win rate against default XGBoost on small-to-medium classification, 87% up to 100k samples, and single-forward-pass parity with a four-hour-tuned AutoGluon ensemble below 10k samples. A [TabPFN-3 report](https://arxiv.org/pdf/2605.13986) exists; its PDF did not parse, so no numbers from it are recorded here.

Three caveats before relying on any of that. RealTabPFN ships under a **non-commercial license**. TabArena, the benchmark producing the win rates, involves researchers from the lab that published TabPFN, so it is not disinterested. And the [2026 review](https://mindfulmodeler.substack.com/p/the-state-of-tabular-foundation-models) that flags both is candid that its author tested "only on toy data".

**[Google TabFM](https://research.google/blog/introducing-tabfm-a-zero-shot-foundation-model-for-tabular-data/) answers the licensing objection** — openly available, trained on synthetic datasets from structural causal models, alternating row/column attention plus row compression, evaluated on TabArena. It is a vendor blog with no linked paper, no stated size limits, and a BigQuery product integration alongside the claims, so treat the numbers as unverified. Try it before TabPFN for label generation anyway, because the licence is the difference between usable and not.

**A distillation route around the gradient blocker (inference, not a paper claim).** TabPFN-2.5 ships a distillation engine that converts the model to MLPs or tree ensembles. A distilled MLP is differentiable end to end, so the chain CatBoost-grade utility → TabPFN → distilled MLP yields a real `∂utility/∂data` without needing gradients through in-context rows, which remains unestablished. Distillation loses fidelity; it is still a cheaper experiment than the redesign it would replace.

**[ZeroGrads](https://arxiv.org/abs/2308.05739) is the published template for what MLU attempts, and MLU is missing all three of its mechanisms.** It learns a neural surrogate of a black-box non-differentiable objective and optimizes through its gradient, using: **locality** (fit to an actively smoothed objective, capacity focused on the current neighbourhood), **online self-supervised training** alongside the parameter optimization with no pre-computed data, and an **efficient sampling scheme** because each objective query costs a full simulator run. Scales to 35k interlinked variables at little overhead. The estimator here is trained offline on a fixed cached label set, globally rather than locally, and never refreshed as the synthesizer moves — the exact configuration in which a surrogate gradient goes stale and the overoptimization curve turns down. If Gate A is attempted, build it this way: local, online, resampled. Caveat: graphics domain, and the objectives there may smooth more gracefully than CatBoost F1 does.

**[PAIRS](https://arxiv.org/html/2605.07972) does not apply here, but the question it raises is cheap.** It pretrains a mean-pool Deep Set encoder on sets of size N ≤ 2, freezes it, then finetunes only the head at arbitrary set size, making training cost essentially independent of deployment set size — end-to-end training at N=1000 took **~100× more compute** for comparable or worse results. The authors state explicitly that this does *not* extend to attention pooling, whose learned queries destroy the additive structure their theory needs. So it is not importable into a PMA/ISAB stack. What it prompts: `SizeScheduler` exists because training at `dataset_size=2048` is expensive, and that is the cost PAIRS removes for mean-pool. **Is attention pooling earning its cost here?** A mean-pool Deep Set baseline scored on `pred_spearman` answers it, and folds into the same sweep as the unresolved Wagstaff bottleneck question.

**[FlashAttention-4](https://proceedings.mlsys.org/paper_files/paper/2026/hash/ae8b0b5838ba510daff1198474e7b984-Abstract-Conference.html)** (MLSys 2026) reaches 1,605 TFLOPs/s on B200 via software-emulated `exp()` on FMA units and conditional softmax rescaling. Its entire premise is Blackwell's asymmetric scaling — faster tensor cores, flat shared-memory bandwidth. Inapplicable on this hardware, and it does not change the SDPA analysis above: attention here is 128×2048 and already linear.

**The ensemble mitigation recorded in the second pass needs qualifying.** Current position is that ensembles **mitigate but do not eliminate** reward hacking, because members can share consistent error patterns in the out-of-distribution region — which is exactly where a surrogate is used during guidance. That is diagnosis point 5 (estimator fed off-distribution decoder tensors) arriving from another field. Newer directions — [behavior-supported regularization](https://arxiv.org/pdf/2503.18130), [Bayesian non-negative reward modeling](https://arxiv.org/html/2602.10623v2), [correlated proxies](https://openreview.net/forum?id=msEr27EejF) — are all 2025-2026, all LLM-domain, none independently replicated. The durable lesson is the qualification: ensembling plus staying on-distribution is the pair, ensembling alone is not.

**The vendored synthesizer slate predates the current state of the art.** TVAE, CTGAN, CTAB-GAN+, LCT-GAN, tab_ddpm and REaLTabFormer are a 2019-2022 slate; current leaders on ML utility are diffusion (TabSyn) and LLM-based (GReaT) generators and their hybrids ([survey](https://arxiv.org/pdf/2503.05954)). This does not invalidate the method, but per the overoptimization result it predicts the outcome: a stronger baseline sits closer to the peak, leaving less headroom for proxy guidance. Any claim of the form "MLU improves strong synthesizers" is currently being tested against a weaker definition of *strong* than exists.

**Flagged, not reported.** [LimiX-2M](https://arxiv.org/pdf/2606.04485) claims to diagnose "low-rank collapse and attention bottlenecks" in tabular foundation models, which would bear directly on the ISAB/PMA stack. The fetch returned a summary generic enough to suspect it was reconstructed from the title rather than the text, so nothing from it is recorded as established. Read it directly if attention capacity becomes a live question.

### Literature review, fourth and fifth passes — meta-learning, transformers, PyTorch (2026-07-31)

**Landmarking is the highest payoff-per-effort item found across all four passes, and it is decades old.** Predicting model performance from dataset characteristics is Rice's algorithm-selection problem (1976), and the standard meta-feature set includes **landmarkers**: run a suite of deliberately weak, fast learners on the table and use their scores as features. Typical suite is 15-25 models — 1-NN, Naive Bayes, Decision Stump, Linear SVM, ZeroR, OneR, random — at **1-10 seconds per dataset**, against a full CatBoost fit for every label `eval_ml_utility()` produces. That cost is the binding constraint on label count, on gate 2's repeated seeds, and on gate 3's held-out calibration.

Two uses. As **features for the random-forest baseline** already recommended, it makes the cheap falsification much harder to dismiss: if landmarkers plus an RF track CatBoost utility at good Spearman, the set transformer must beat that, not nothing. **Done 2026-08-08** — see "Random-forest-on-landmarkers baseline" and "Big wins implementation" (`ml_utility/landmarkers.py:LandmarkerProxy` promotes this from a one-off script measurement to reusable cheap-relabeling code). As a **differentiable proxy**, a logistic-regression or linear-SVM landmarker trained on the synthetic table and scored on real data is differentiable through the synthetic data by unrolling a few solver steps or by implicit differentiation — the smallest possible instance of the dataset-distillation idea, satisfying its differentiable-downstream-model requirement with a model that costs a second. The risk is specific and must be tested, not assumed: a linear landmarker's gradient points toward linear separability, not CatBoost utility, so it stays behind Gate A like everything else. **Not implemented** — this is the differentiable-proxy idea, distinct from the RF-baseline use above.

**A 2026 negative result caps how far meta-features can be pushed here.** [Revisiting Metafeatures to Explain Model Differences on Tabular Data](https://arxiv.org/html/2605.28418), over 51 TabArena datasets: only two associations survived false-discovery control, one of which failed to improve prediction on unseen datasets, and **for neural networks vs tree-based models no meta-feature survived screening at all**. Their conclusion is that "global meta-features provide at most weak routing signal". Their task is model-family *routing*, not predicting one fixed model's score, so this does not kill landmarking. What it does say is that 51 datasets against hundreds of candidate features was already too thin for most patterns to survive proper controls — and this project has **four**. That is the strongest available argument against learned dataset embeddings (Dataset2Vec, Task2Vec) at this scale, and for a handful of landmarkers with a mechanistic reason to correlate instead.

**The estimator is a neural process, and that framing is worth adopting.** Predicting a target from a context set, amortized across tasks, permutation-invariant, with uncertainty — that is the neural process family. [Transfer Neural Processes](https://proceedings.mlr.press/v139/wei21c.html) (Wei et al., ICML 2021) does exactly this for hyperparameter performance prediction across datasets and reports state of the art in "at least one order of magnitude less trials". Adopting the framing supplies the uncertainty estimate that the conservative-scoring mitigation (second pass) requires. **The uncertainty need itself is met 2026-08-08** by `estimator/selection.py:conservative_score`'s ensemble variance (see "Big wins implementation") — no separate distributional-head architecture change was made; the neural-process *framing* as a lens for redesigning the architecture itself remains unexplored.

That literature also **partially settles the Wagstaff question flagged in the second pass**. The known defect of neural processes is underfitting — inaccurate predictions even at their own context points — attributed to "the limitation of summaries with prespecified finite dimensionality in representing context sets of arbitrary size" and to mean/sum pooling failing to capture context-query interaction, with **attention as the accepted remedy**. That is the latent-width bottleneck appearing as an observed practical failure rather than a theorem about sum-decomposable functions, and it puts PMA on the right side of the argument. Reframe the open question from "does the theorem bind" to "is `head_n_seeds=1` enough attention capacity at `dataset_size=2048`". It also weakens the mean-pool baseline prompted by PAIRS in the third pass.

**Profile before optimising — this supersedes the ordering given in the first pass.** Current PyTorch guidance is to measure first, profiling a short window after warmup rather than a whole run, and to expect the DataLoader to be the culprit: the most common cause of GPU underutilisation is the CPU failing to feed it, with `num_workers > 0` and `pin_memory=True` as the first fix. Excess `synchronize()` is separately called out for distorting measurements and hiding compute/transfer overlap. Both named anti-patterns are present here — `dataloader_worker=0` is the default in `load_dataset`, and there are about twenty forced syncs per batch. So the correct first move is `torch.profiler` over ~30 steps post-warmup, **not** the SDPA and bf16 changes recommended earlier: if the loop is input-bound, every kernel optimisation buys nothing because the GPU is already idle waiting on the CPU. With `dataloader_worker=0` and an in-memory cache, input-bound is the live hypothesis.

**Python 3.9 is a ceiling on PyTorch, and that matters before profiling.** PyTorch 2.9 (October 2025) raised the minimum to **Python 3.10**, and this project targets 3.9 with pinned forks of torchtext 0.6.1 and optuna. Everything in 2.9 and 2.10 is therefore unreachable without an interpreter upgrade the torchtext fork may not survive. What is on the other side: PyTorch 2.10 (January 2026) added **combo-kernels horizontal fusion in Inductor, explicitly to lower kernel launch overhead** — which is the exact win profile for a small model issuing many tiny kernels, and this model is small (`d_model` 256, six layers, batch 2-4). Nothing here justifies breaking a working environment on speculation, but it determines what the profile is *for*: if the step turns out to be dominated by launch overhead and gaps rather than kernel time, the fix is a PyTorch upgrade gated behind a Python upgrade gated behind the torchtext fork. SDPA itself needs only 2.0, so the first-pass recommendation stands either way.

**FlexAttention is ruled out, for a specific reason.** [FlexAttention](https://pytorch.org/blog/flexattention/) compiles a fused kernel from a user-supplied `score_mod` and covers causal, sliding-window, document masking and additive biases within 10% of FlashAttention-2 on Ampere. But `score_mod` is an elementwise transform of the attention scores **before** softmax; the softmax itself is fixed. The searchable `softmax` parameter here replaces the normalisation, not the scores, so FlexAttention cannot express it — and without `torch.compile` it materialises the full score matrix, which is worse than the current code. Since custom softmax is commented out of the search space and `nn.Softmax` is the operative default, plain SDPA already covers the case.

**A formal statement of diagnosis point 5, and a bound on ambition.** [In-Context Learning Is Provably Bayesian Inference](https://arxiv.org/abs/2510.10981) (Wakayama & Suzuki) decomposes total in-context risk into two orthogonal terms. **Bayes Gap** — distance from the Bayes-optimal in-context predictor — is bounded in terms of the number of pretraining prompts and their context length, and the OOD analysis shows it is **sensitive to Wasserstein shift between pretraining and test prompts**. **Posterior Variance** is model-independent and set purely by the difficulty of the true task; it is irreducible.

The theory is proved for a uniform-attention transformer, so its constants will not transfer to an ISAB/PMA stack and should not be quoted. The decomposition is what is useful, twice over. First, it formalises diagnosis point 5: "trained on preprocessed real/augmented tables, fed raw decoder tensors at guidance time" *is* a Wasserstein shift between training and test prompts, and this is a proof that excess risk is sensitive to it. Second, it bounds what any of this work can achieve — part of the surrogate's error is irreducible, and no architecture change touches it. **Measure that noise floor**: refit `eval_ml_utility()` on identical inputs across seeds and see how much residual variance is CatBoost's own. If it is most of `pred_rmse`, the architecture and efficiency programme is optimising the wrong term. That experiment is cheap, has never been run, and calibrates every other open question in this file.

**Depth is not the constraint here.** TabPFN-2.5 and TabPFN-3 report markedly improved accuracy from increasing attention depth to 18 and 24 layers, against this body's 4 encoder + 2 decoder. The datum is real and the inference does not transfer: those models are pretrained on hundreds of millions of synthetic datasets, so depth buys approximation capacity their data volume supports. At ~400 labels per dataset it buys overfitting, which is also what the small-data literature below says. Read it as one more argument that labels, not capacity, are binding.

**Small-data transformer practice, and one result that bears on reading results.** The low-data regime leans on regularisation — dropout around 0.3-0.5, stochastic depth, early stopping — because a transformer's weak inductive bias gives it little else. More useful: in low-data regimes early-stopped transformers approach simpler predictors with **shorter effective context**, with early stopping apparently selecting effective context length automatically. Consequence for this repo: a small `pred_rmse` gap between two architectures may be an early-stopping artifact rather than an architecture result. And since `layer_norm` is pinned False everywhere while `dropout` is searched, the model trains with no normalisation at all in exactly the regime where the literature says regularisation matters most — check what the `BEST` configs actually chose for `dropout` before adding capacity anywhere.

## Running

There is no test suite, lint config, or CLI entrypoint. This is experiment code driven from notebooks/scripts that call the pipeline functions directly, plus Optuna studies for hyperparameter search. Work with it by importing and calling the pipeline functions; wire up a small script rather than expecting a `main`.

Typical estimator flow (all in `loss_learning/estimator/pipeline.py`):
1. `augment_2()` / `augment_kfold()` — take a raw dataset from `datasets/`, produce augmented (degraded) variants, and score each with `eval_ml_utility` to create labeled (synth, real) utility pairs. Outputs land in `aug_train/`, `aug_val/`, `aug_test/`, `bs_*` (bootstrap), keyed by dataset name.
2. `load_dataset_3()` / `load_dataset_4()` — assemble the cached, preprocessed multi-source datasets for train/val vs. test.
3. `train()` / `train_2()` / `train_3()` — build the model via `create_model` and run the training loop (`train_3` adds a `SizeScheduler` that ramps dataset/batch size). Returns the model + loss history + eval.

Optuna objectives wrapping the above live in `estimator/study.py` (`objective`, `objective_2`); actual `optuna.create_study` calls belong in the caller's script/notebook.

The `synthetics/` and `synthetics2/` dirs hold generated synthetic samples per synthesizer per dataset; `models/` holds trained synthesizer checkpoints (lct_ae, lct_gan, realtabformer, tab_ddpm, tvae) that the estimator consumes.

## Estimator model architecture

`MLUtilityWhole` (`estimator/model/models.py`) = **Adapter(s) → Body → Head(s)**, assembled by `create_model()` in `estimator/model/pipeline.py`:

- **Adapters** (`nn.ModuleDict` keyed by synthesizer name, e.g. `tab_ddpm_concat`, `tvae`, `lct_gan`): per-synthesizer MLPs that project that synthesizer's differently-shaped latent/feature vector into the shared `d_model`. Input dims in `DEFAULT_ADAPTER_DIMS`.
- **Body**: either `Transformer` (encoder→decoder) or `TwinEncoder` (two encoders combined via `CombineMode`), selected by `Body=` / `ModelBody`. Built on ISAB/PMA set-transformer blocks (`estimator/model/blocks.py`, `layers.py`, `modules.py`) with configurable LoRA (`LoRAMode`), ISAB (`ISABMode`), and PMA options.
- **Head(s)**: MLP producing the scalar utility (`heads=["mlu"]`).

`MLUtilityWhole[model_name]` returns a lightweight `MLUtilitySingle` view (adapter + shared body + head) and caches it. **One synthesizer is the `fixed_role_model`** (default `tab_ddpm_concat`) — it's the "role model" whose gradient supervises training; other synthesizers are trained to agree with it (`non_role_model_avg`, `non_role_model_mul`).

The training loss combines prediction loss (MSE to CatBoost value), optional heuristic gradient penalties (`calc_g_loss` and friends in `estimator/process.py`), and std/mean-prediction penalties. The gradient penalty is disabled by default because it is not supervised by true-utility gradients. A `LossBalancer` (`ml_utility_loss/loss_balancer.py`) weights these terms. The heavy lifting of a training step is `train_epoch` / `eval` in `estimator/process.py`.

## Hyperparameters and the params/ convention

Enums and registries mapping string names → classes/functions (activations, optimizers, losses, softmaxes, all the `*Mode` enums, `GradientPenaltyMode`) live in **`ml_utility_loss/params.py`**. Optuna search **spaces and defaults are per dataset**, duplicated across generations of the experiment:

- `estimator/params/`, `params2/`, `params3/` — search spaces for the estimator, one module per dataset (`contraceptive.py`, `insurance.py`, `treatment.py`, `iris.py`) plus `default.py`. `params3` is the newest; prefer it. Each defines `DEFAULTS` and `PARAM_SPACE`.
- `ml_utility/params/` — search spaces for the CatBoost ground-truth model.

Params flow through `ml_utility_loss/tuning.py` (`unpack_params`, `pop_repack`) and the `sanitize_params` / `force_fix` / `check_params` machinery in `params.py`, which validate an Optuna trial's params against a `PARAM_SPACE`, coerce out-of-range categoricals to defaults, and translate the special `int_exp_2` / `log_int` / `log_float` distribution tuples. `NON_MODEL_PARAMS` in `estimator/model/pipeline.py` lists keys that are training/tuning knobs, not model-constructor args — `remove_non_model_params` strips them before building the model.

When editing a param, note there are 3+ parallel copies (per dataset × per generation) — grep the whole `params*/` tree so you don't update only one.

## Conventions worth knowing

- **`init=False` is threaded everywhere.** Submodules are constructed without initializing weights; the top-level container (`MLUtilityWhole` / `MLUtilitySingle`) calls `.init(activation=...)` once so the final activation is applied only to the last layer. When adding a module, honor the `init` flag and expose an `.init()`.
- Every model takes `device=DEFAULT_DEVICE` and calls `self.to(device)` in `__init__`.
- Category features, task type, and target column for each dataset come from the sibling `datasets/<name>.json`.
- `transformer/` and `transformer_debug/` at the repo root are a vendored copy of jadore801120's "Attention Is All You Need" implementation, kept for reference — not part of the `ml_utility_loss` package.
